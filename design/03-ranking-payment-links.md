# 累计打榜、资金与链接业务规则

本文件是相关业务的唯一规则源。每个大品类一个累计总榜，不清零、不按日期划分竞赛周期。

## 1. 最小打榜模型

公开条目 = 品牌名 + Logo + 当前品类有效打榜额 + 名次。
表单必填仅 displayName、logoAssetId、amountFen。categoryId 从已选品类带入；账号用于管理和付款归属，不增加经营资料字段。
店铺、直播、介绍、联系方式、地址、主体认证、品牌库关联均可缺省。
首次提交只校验名称/图片和金额；选填链接未审核或被退回，不影响无问题的基础条目。

数据术语：
- merchant：一个账号可管理的“推广品牌档案”，不是强制提供营业执照的法律主体。
- merchantCategory：推广品牌参加某个大品类的唯一累计条目。
- order：购买该条目展示推广服务的一笔订单。
- receipt：支付渠道确认的实际收款。
- rankLedger：从合格收款和成功退款派生的不可变排名流水。

## 2. 金额和排名算法

人民币 CNY；数据库 BIGINT 存分。API 为安全整数，禁止浮点元和客户端自行计算最终金额。
首版默认最低单次 ¥100（10000 分），最高 ¥100,000（10000000 分），只允许整数元；后台配置与校验响应同步。
有效打榜额的展示不扣除平台通道手续费；通道成本与平台净收入在财务侧另外核算。

对某个 merchantCategory：
grossFen = 合格成功收款所产生的 CREDIT 流水总额
refundedFen = 对这些收款的成功 REFUND 流水绝对值总额
netFen = grossFen - refundedFen
必须满足 0 <= refundedFen <= grossFen。

同一笔订单只属于一个大品类；不能同时给耳机、电脑各加全额。
同一个品牌在电脑投入 ¥500、耳机投入 ¥300，分别出现在两个榜上，不能显示为各 ¥800。
不存在将两类混排的跨品类资金总榜。财务汇总可以跨类，不能作为另一张排名。

正式排序：
1. netFen 降序；
2. attainedAt 升序；
3. merchantCategoryId 字典序升序，作为确定性兜底。

attainedAt 定义为“本条目当前净额最近一次发生变化的已提交流水时间”，由服务器生成。
退款降低净额时也更新 attainedAt，不追溯借用更早时间抢同额名次。
同一数据库时间戳可相同，最后一级 ID 让结果始终一致。
净额为零、审核隐藏、封禁条目不出现在公开付费榜，不能显示负数名次。

品牌榜与该算法没有共享评分；公开自然访问、点击也不改变资金榜排序。
金额不等于商家资产、产品质量或自然人气；首屏写明“商业推广，按累计有效打榜投入排序”。

## 3. 累计榜与退款口径

追加投入永久累积，没有到期归零或换期规则。
退款无论何时发生，都扣回原 merchantCategory，不影响其他品类；成功退款前不扣榜额。
历史快照用于审计和排查，不面向用户包装成月榜或周期榜。

公开条目可展开查看累计实付、累计已退、有效打榜额、最近变动时间。
“累计实付”仅包含获得榜额的合格订单；已扣款但待退款的异常交易在私有账单单列，不能偷偷变成排名资金。
财务所有收款都在 receipt 中记录；排名账本只接纳经过匹配的订单。两者通过异常队列对账。

条目下线：隐藏榜位并保留账本；重新审核通过后按现有有效累计重回排序。
下线不自动产生退款，也不代表拒绝应退金额；退款依据具体订单和服务协议处理。
改名/改 Logo 需版本审核，不能把无关新品牌继承为老品牌的推广荣誉；重大变更单独处理并展示变更记录。

## 4. 预计排名与订单创建

GET quote 返回：当前净额、最低/最高金额、指定追加金额、预计净额、预计名次、boardVersion、有效期 60 秒。
预计名次按请求时榜面计算，不锁定榜位。按钮写“预计升至”，不能写“购买第 1 名”。
若提供“一键超过上一名”，建议金额 = max(最低单次金额, 上一名净额 - 自身净额 + 100 分)，并按整数元约束取整。
超过单次上限时说明需要分次投入，不承诺最终位置。

创建订单：
- 要求有效登录、档案管理权限，名称/Logo 已通过基础审核，大品类启用且允许展示。
- 不检查店铺/直播/简介是否填写。
- Idempotency-Key 必填，作用域为用户 + 操作；同键同请求复用结果，同键不同请求返回 409。
- 订单固化 merchantId、categoryId、amountFen、currency、渠道、服务条款版本、15 分钟 expiresAt。
- quote 过期返回 QUOTE_EXPIRED 让用户刷新；不要提交后自动替换用户确认的金额。
- 若渠道未开通，返回 PAYMENT_CHANNEL_UNAVAILABLE，不能返回假支付成功。

## 5. 支付状态机与幂等

订单状态：CREATED → PENDING → PAID；未付款可以 CLOSED。
退款状态单独记录：NONE / PROCESSING / PARTIAL / FULL，不把 PAID 改写成“从未支付”。

渠道 success 回调处理：
1. 验签/解密，核对收款主体、渠道 App 标识、订单、CNY、金额与渠道实际成功状态。
2. provider + transactionId 唯一；一个订单只有一个 accepted receipt。
3. 获取订单与 merchantCategory 行锁；重复回调返回已处理结果。
4. 数据库事务写 receipt、PAID、CREDIT 流水、累计余额与 attainedAt、outbox。
5. 提交后再 ACK 渠道；异步失效榜单缓存，目标 5 秒内刷新。

客户端支付 SDK 返回、网页重定向、用户回到 App 都不能触发入账。
SDK 成功后先查服务端订单；用户离开收银台也不能仅凭前端取消认定未付款。
客户端自动查询最多 30 秒，之后显示“结果确认中，可稍后查看”，后台补偿查询继续运行。

迟到和异常：
- 渠道 paidAt 在订单有效时间内：即使回调晚到或本地先关单，也按真实结果入账一次。
- paidAt 超过订单有效期：记录实际收款，走异常原路退款，不增加榜额。
- 同订单不同渠道交易发生重复扣款：只有 accepted receipt 计榜，额外收款独立登记并原路退回。
- 金额/币种/身份不符：隔离收款，人工复核或退款，不能污染榜额。
- 回调乱序、重放、服务重启都靠数据库约束和事务处理，不能只靠 Redis 去重。

安全支付取值：所有金额 <= 9000000000000 分，JSON 使用整数；单次限额远低于该值。服务端累计越界则拒单。
回调原文仅保留必要审计内容；日志不记录密钥、完整支付凭证、手机号和身份证件。

## 6. 退款和对账

退款实体状态：REQUESTED → APPROVED → PROCESSING → SUCCEEDED；可 REJECTED 或 FAILED。
每笔退款必须绑定原 receipt/order，成功退款总额不得超过该收款。并发部分退款需锁定原支付行并计入已批准处理中金额做限额检查。
仅渠道确认成功后追加负流水；重复退款回调不重复扣榜。失败则不扣榜，保留原因。
关联 order 的退款影响原 category，不能用当前页面分类来选择。

政策默认：
- 重复扣款、收款与服务不匹配、技术原因未生效：全额原路处理。
- 已展示服务的退款按已告知的服务条款和实际情况审核；系统必须支持部分与全额退款，不把“绝不退款”写死。
- 管理员不能以“调整金额”修改余额；补偿更正要有独立原因、双人审批和可追溯流水。

每日对账：渠道收款/退款 ↔ receipts/refunds ↔ rankLedger ↔ materialized balance。
差异进入工单，保留责任状态。发现漏记按原交易补偿，发现重复不能删除原始流水掩盖问题。
账本、展示累计、平台收入是三种口径；跨品类汇总时只能按订单汇总一次。

## 7. 缓存和实时性

PostgreSQL 是金额真相源；Redis 仅作缓存和刷新队列。
首版数据库按复合索引排序，缓存整体榜面版本；不强依赖 ZSET 的字典序处理同额时间。
API 返回 boardVersion、updatedAt 与完整金额口径。
同一次翻页沿用 snapshotId；快照过期返回 BOARD_SNAPSHOT_EXPIRED，客户端刷新首屏，防止排序变化导致重复漏项。
有更新时显示“排名已更新，点击刷新”，不在用户手指下突然移动卡片。
支付完成页可读取强一致私有累计，并提示公开榜刷新中。

## 8. 店铺、直播和视频链接

所有链接均选填，数据存在才渲染入口。允许：
- SHOP：店铺/品牌经营页面。
- LIVE：直播间或直播主页。
- VIDEO：外部介绍视频。
- WEBSITE：介绍网站。
一个档案在每个大品类可配置多个链接；每种首版最多 3 个，指定一个主入口。

存储原始 HTTPS 地址、平台、展示标题、审核状态、可选到期时间。默认不接受用户直接提交任意自定义 scheme。
平台适配器基于已核验域名和公开官方能力生成跳转动作；未经验证的平台只做 HTTPS 和复制。
链接审核与基础条目分离：某链接不通过仅隐藏该链接。

安全边界：
- 仅 HTTPS；拒绝 javascript/data/file、用户信息 URL、内网/环回 IP、非允许域和恶意嵌套跳转。
- 服务端健康探测与预览抓取限制 DNS/重定向/出网，防 SSRF；不读取用户浏览器登录态。
- 自有出站路由只接受 linkId，不接受任意 ?url= 变成开放跳转器。
- 原生 Universal Link/App Link 白名单单独配置，失败回退 HTTPS。
- Web 在用户点击同步发起导航，避免异步 API 后打开新窗被拦截；可用预解析动作或当前页受控中转。
- 目标平台登录、App 安装情况、微信内置浏览器限制都可能影响成功；不承诺所有环境一键直达。

客户端步骤：点击 → 展示目标平台/域名 → 选择打开 → 系统处理 → 失败给 HTTPS/复制/取消。
copy-only 不弹出“跳转成功”。返回 App 保留当前页面、筛选和滚动位置。

直播状态：UNKNOWN、SCHEDULED、LIVE_CLAIMED、OFFLINE。
商家标记 LIVE_CLAIMED 最长有效 30 分钟，可续期；过期自动回 UNKNOWN。
前台写“商家标记直播中·X分钟前确认”，不能伪造第三方实时在线认证。
没有官方 API 凭证不抓取登录保护页面、不把 HTTP 200 当成正在直播。

## 9. 支付与平台能力

Apple 官方 3.1.3(g) 已核对；同一 App 广告展示的购买有 IAP 要求，例外有条件。
默认可开发闭环：独立 Flutter Web 商家中心 + 合法开通的 Web 收银台；各原生渠道显示能力由服务端 capability 决定。
iOS 首发默认只浏览与管理，不显示外部购买引导；后续可实现合规 IAP 产品与服务端交易验证。
Android 各商店/地区分别适配；不能因 Flutter 跨平台就默认同一支付插件在所有商店允许。
开发环境用独立沙箱适配器，页面明显标“演示”；生产未配置渠道时真实支付关闭。禁止通过 WebView 假装绕开商店要求。

## 10. 数据统计口径

记录 board_impression、merchant_open、shop_click、live_click、video_click、launch_attempt、launch_accepted、launch_failed、copy_link。
launch_accepted 只表示系统接受打开请求；不能解释成直播观看或订单成交。
点击有 eventId 幂等与基本去重；统计为估算有效点击，不能作为资金账本。
跨站实际观看、成交必须得到合法官方回传才另行展示。
