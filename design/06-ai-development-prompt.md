# 给开发 AI 的启动指令

复制以下内容到已选定的应用开发项目。把本设计包作为项目文档一起提供。
这是开发指令文本，不代表本轮已经授权创建仓库、部署或发送外部消息。

---

你是本项目的开发负责人。请依据 docs/ 中的设计包完成一个可运行的 Flutter 跨平台产品“品阶”（暂名），包括客户端、真实后端、运营后台、数据库和必要测试。

先依次读取 README、01-product-prd、02-flutter-ux、03-ranking-payment-links、04-architecture-data、05-delivery-acceptance 和 contracts/ 全部文件。
如与当前用户新要求冲突，以用户新要求为准并同步修订规格。

## 必须保持的产品要求

1. 手机端体验优先，用 Flutter；Android、iOS、Web 共用业务层，桌面自适应并按支持环境构建。
2. 商品大品类只有一层，如耳机、电脑、手表。不创建蓝牙耳机、笔记本电脑等子品类或子榜。
3. 所有大品类可扩展；首发 24 类见种子。不要把任务收缩为只做手表。
4. 品牌内容围绕品牌地位、辨识、圈层认可、身份表达、为什么愿意购买、赞誉和争议；公开表达体面。
5. 品牌内容榜与商家商业榜明确分开。
6. 每个大品类只有一个商家累计总榜，持续累计、不做月榜、不清零、不做跨品类金额混排。
7. 打榜必填仅品牌名、展示 Logo、金额。当前品类自动带入。店铺、直播、介绍、电话、经营主体证明等全为选填。
8. 没有任何链接也能付款和上榜；选填项未填不拦截，不渲染空按钮。
9. 公开展示实际有效累计金额；排名只能由服务端成功收款和成功退款计算，不允许手改。
10. 直播是可选外部跳转，不先做自建直播系统。平台跳转失败时有 HTTPS、复制或返回方案。

## 技术与实施

按规格固定 Flutter + Riverpod + go_router + Dio；NestJS + PostgreSQL + Redis；React 运营后台。
先检查现有项目、AGENTS.md、技术环境和未提交改动。已有仓库遵守先拉取的用户约定，不能覆盖无关工作；没有用户提供的仓库不要擅自 git init。不要自动 push。

按 M0 → M5 实施，每阶段交付能运行的结果并更新任务状态。
不要只写方案、静态首页或 mock 商家列表后就结束。缺少真实渠道时仍可完成真实本地 API/数据库和显式沙箱适配器。
不要向用户索要聊天中的密钥；提供环境变量模板与开通说明。未配置功能要清楚显示未开通。
不要编造商品口碑、来源、支付、访客或直播数据；所有 demo 有标记且不进入生产种子。

资金以整数分处理。先实现不可变流水、幂等和事务测试，再接 UI 支付结果。
回调验签后才入账；SDK 返回不代表付款完成。
退款扣原大品类，且只在渠道确认后扣累计；账本不可静默修改。
API 必填字段、数据约束与 ranking-cases 一致；不同语言客户端不能各算一套排名。

支付按发行渠道适配：独立 Web 商家中心可走已开通 Web 支付；iOS 同 App 广告购买不能简单用外部链接或 WebView 绕过，依照当前官方规则开通能力。默认 App 不提供未经允许的购买引导。
Flutter 共享代码不代表支付/外链插件自动支持所有系统，必须实现 capability 接口和降级。

## 自主处理与交付

常规视觉、组件与实现细节按设计执行，不反复征求同一需求。遇到缺少外部凭证，完成独立工作并列出接入点。
重大业务规则仍有歧义时，先指出具体冲突，不能悄悄改成周期榜或复杂入驻。
测试核心浏览、三项打榜、无链接上榜、跨品类隔离、重复支付回调、退款、权限、外链失败和大字体。
仅报告实际执行的平台测试，Windows 上没有 macOS 构建环境就明确 iOS/macOS 尚未编译验证。
最终给出源码位置、启动方法、真实测试结果、演示账号生成方式、构建产物与仍需开通的事项。
本地修复和验证持续推进；正式发布、真实收款开关、应用商店提交和生产部署按本次会话实际授权执行。
