# 产品需求规格

## 1. 定位与目标

一句话：看懂一个品牌在人群中的位置，找到符合自己身份表达的选择，再发现愿意公开展示投入的商家。

核心心理顺序：希望被认可 > 想显得有品味 > 不想花钱却没人看出来 > 害怕选错和被懂行的人否定。
“虚荣心”是内部产品洞察，公开使用“品牌地位、辨识度、圈层认可、风格、场合”等表达。
不把用户划分为穷人或富人，不用商品定义人的价值。

可用宣传语：
- 看懂品牌，再做选择。
- 同样的预算，不同的表达。
- 一个牌子，值得被谁看见？

首版目标：用户能在 3 分钟内理解一个大品类的主要品牌差异，完成 2–3 个品牌对比，并按需进入商家店铺或直播。

## 2. 品类规则

品类只有一层，实体没有 parentId。正式初始列表见 categories.json。
24 个大品类：手表、箱包、珠宝、服装、鞋、配饰、香水、美妆护肤、汽车、摩托车、自行车、游艇、酒、手机、电脑、耳机、音响、相机、电视、家电、家具、文具、运动装备、户外装备。

“蓝牙耳机、头戴式耳机、笔记本电脑、台式电脑”不建立子品类、不建立子榜、不作为商家另付费入口。
功能形态可写在商品描述里；风格、预算、场合可用于筛选，但不生成新的品类 ID。
后台新增同样粒度的大品类即可扩展全品类覆盖。

品牌与品类为多对多：同一品牌的电脑、手机、耳机定位独立。不能把一个品类的档次或评分自动复制给另一品类。
同一商品有一个主品类；电视归电视，不重复作为家电榜商品。品牌可同时在电视和家电有真实的品牌资料，但不重复计算商品。

电脑、耳机等并非所有品牌都属于传统奢侈品。本平台关注其品牌溢价、消费形象和高端定位，不把“售价高”直接写成奢侈地位。

## 3. 人群、角色与权限

| 角色 | 主要行为 |
|---|---|
| 游客 | 浏览品类、品牌榜、品牌介绍、对比、商家榜、店铺或直播外链 |
| 注册用户 | 游客能力 + 跨端收藏、关注、消息、反馈、创建推广品牌 |
| 商家成员 | 管理所属商家资料、链接、直播状态、查看榜位与账单；OWNER 可付款和管理成员 |
| 内容编辑 | 编辑资料、依据与榜单草稿，不能自己完成最终发布 |
| 审核员 | 审核品牌、商家和链接，发布版本，处理反馈 |
| 财务 | 对账、审核退款，不能直接改榜位和累计金额 |
| 管理员 | 权限与配置；敏感动作审计，不能删除资金流水“改排名” |

浏览和跳转不强制登录。登录只发生在需要账号的动作上，并在完成后回到原位置。
商家榜中的“品牌名”是商家自填的推广展示名，不自动关联品牌库、不自动代表品牌官方。主体与官方授权核验均为可选增强功能，不是打榜必填项。

## 4. 品牌内容与排行

每个品类默认一个“品牌地位榜”，由编辑审核发布，排名有明确理由和版本。
次级排序“辨识度、圈层认可”在已有资料充分时提供；首版不凭空生成多套精确分数。

品牌卡片：
- 名称、官方拼写、发源地、品牌图片或文字标识。
- 当前品类的定位层级、排名、20–40 字定位说明。
- “大众辨识 / 圈层认可 / 身份表达 / 风格辨识”标签。
- 已审核、待补充或演示标记，更新时间与依据入口。
- 收藏、对比操作。

品牌详情的固定结构：
1. 一句话理解：面向哪些消费语境，擅长表达什么。
2. 市场定位：主要商品、价格带、可比品牌；价格必须有地区、币种、时间、新品或二手口径。
3. 为什么有人愿意买：辨识度、风格、象征意义、品牌故事、自我奖励、收藏等。
4. 谁更容易认可：大众、爱好者、特定场合；只表述有证据的样本与编辑判断。
5. 常见赞誉与争议：每条独立来源；不能用少数帖子代称“全网都认为”。
6. 代表系列：最多 3–6 个，避免首屏变商品货架。
7. 适合与需要考虑：场合、显眼程度、搭配、持有成本；工艺参数作为支撑而非唯一主轴。
8. 同预算对比、相近品牌。
9. 商家与直播：单独模块，带“商业推广”。
10. 引用、修订记录、纠错。

定位层级默认五档：殿堂级、奢华级、高端级、精品级、进阶级；允许该品类配置不适用。
它是平台编辑框架，不是官方认证或用户身份评级，不同品类档位不直接等值。
标签采用“较高 / 中等 / 较低 / 资料不足”，不伪造样本量和 98.7 之类精度。

品牌榜排序由版本化的 editorial_rank 决定。发布时要求：
- 该品类至少 5 个品牌资料；不足则展示资料目录和“榜单待完善”。
- 每个上榜项有结论、理由、来源和复核人。
- 每版同一品牌只出现一次，名次连续且唯一。
- 商家支付不参与品牌榜排序。商家本身的资金榜另行展示。

## 5. 消费端 P0 功能

| 编号 | 功能 | 完成条件 |
|---|---|---|
| C01 | 一层品类目录 | 24 类可进入，同一套分类用于品牌榜、商家榜和入驻 |
| C02 | 品牌搜索 | 中文名、英文名、别名、拼音命中；分类内和全站搜索明确 |
| C03 | 品牌榜和详情 | 最新已发布版本、依据、更新时间、缺失资料状态 |
| C04 | 品牌对比 | 同品类最多 3 个，比较地位、辨识、场合、价带与争议 |
| C05 | 收藏与关注 | 登录后跨端同步；游客对比可本地临时保存 |
| C06 | 商家累计榜 | 按所选大品类累计有效打榜额排名，公开金额 |
| C07 | 商家详情 | 品牌名、Logo、金额必有；介绍、店铺、视频、直播等仅在选填后展示 |
| C08 | 外部跳转 | 用户主动点击，展示目标平台，有可用的失败处理 |
| C09 | 分享 | 分享品类、品牌、对比和商家链接；海报标注来源和日期 |
| C10 | 纠错与举报 | 理由、提交反馈、后台处理状态，不强迫公开个人资料 |

首版“直播”是外部直播入口，不包含主播端、推流、弹幕、礼物、实时推荐算法或自营直播交易。
外部介绍视频优先跳转；有合法托管素材时可在站内播放短介绍，默认不自动播放。

## 6. 商家端 P0 功能

核心路径：进入某大品类商家榜 → 我要打榜 → 填品牌名、上传 Logo、输入金额 → 登录或恢复账号 → 确认付款 → 累计金额和榜位更新。
当前品类由上下文带入；支付与服务条款用系统确认，不要求额外经营资料。

必填仅三项：
1. 品牌名：2–40 个字符，公开展示。
2. 展示 Logo：上传图片，审核可用。
3. 本次打榜金额：人民币整数元，符合最低金额与限额。

其他均选填：品牌介绍、店铺链接、直播间链接、介绍视频、联系方式、城市、关联品牌库、主体资料、授权凭证。
缺少任何选填项，不得阻止建档、支付、上榜或后续追加；不展示“资料未完善所以不能打榜”的流程。

- 名称和 Logo 做基础内容审核，不默认索取营业执照、地址、联系人或官网。争议处理是独立流程。
- 一个账号可拥有多个推广品牌；一个推广品牌在同一大品类只有一个累计条目。品牌可参加多个大品类，但资金分开。
- 同名不自动合并不同账号的资金。账户内重复品牌名提示复用已有档案；他人同名及冒用争议进入审核。
- 未付费档案在用户自己的管理页可见，金额为零不占榜位。
- 无店铺、直播、视频或介绍时，公开条目只展示品牌名、Logo、累计金额、名次及规则；点击可看金额说明，不制造空详情页。
- 选填资料可在首次上榜后随时添加；链接审核不影响原有合规的基础条目展示。
- 前三名可突出展示，但不能遮挡“商业推广”和金额口径。
- 支付前展示所选品类、有效累计、本次金额、预计名次及退款政策；名次不锁定、不保证永久第一。
- 资金展示为累计实付、累计已退、有效打榜额；每一项可追溯。
- 直播、店铺等选填后提供访问统计；没填时不显示无意义的零数据面板。
- 自报直播状态有来源和有效期；没有第三方回传时不显示观看人数、成交量或 GMV。

## 7. 运营后台

导航：工作台 / 品类 / 品牌与系列 / 品牌榜版本 / 商家审核 / 链接审核 / 内容反馈 / 订单 / 退款与对账 / 展示配置 / 用户权限 / 审计。

必须支持草稿预览、双人复核、版本发布与回退、定时下线、理由记录。
回退内容不回退支付账本；隐藏推广品牌只改变展示资格，不抹去财务记录。
大品类删除改为停用。存在品牌、商家或资金记录时不能物理删除。

## 8. 数据与内容生产

内容字段拆为 factual、editorial、community 三种：
- factual：官网、可靠档案、公开价格等事实与引用。
- editorial：平台编辑判断，带适用市场、理由和复核人。
- community：真实收集的用户反馈，带样本范围；样本不足就不展示统计。

AI 可辅助提取、翻译、写初稿和找缺失字段；未经来源核对与人工审核不能自动发布品牌地位结论。
不要伪造论坛评价、访客数、榜单购买、店铺、支付成功或直播状态。
图片记录来源和使用权；没有可用资产时显示文字标识。演示素材与真实素材隔离。

正式首发内容目标：24 类均有至少 5 个审核品牌品类档案、一份有效品牌榜。
内容丰富度是运营交付，不要求开发 AI 编造 120 份真实口碑。
开发演示种子每类至少 3 个明确标注“演示”的资料项，用于页面全覆盖；未满足 5 个的榜单按规则显示待完善。

## 9. 收入和增长

主收入：品类累计榜上的真实推广投入。首版不叠加入驻年费、付费认证和会员墙，降低理解成本。
后续：有披露的商业专题、专业咨询、获得合法回传后的导流合作。不得用付费购买品牌档次。

用户增长入口：品牌对比分享、品类档位卡片、场合选择内容、用户收藏。
商家增长入口：免费建档、真实访问数据、公开投入与名次、可分享的商家荣誉卡。
荣誉卡写“某品类商家推广榜第 X，截至某时，有效打榜额 ¥X”；不能写成官方质量评奖。

要验证：内容是否促成对比与收藏；公开金额是否增加点击；商家点击质量和追加投入是否成立。
不把付费额等同自然人气或经营资产。对外可称“商家热度榜”，首屏同时解释“按累计有效打榜投入排序”。

## 10. 优先级

P0：上述完整浏览、内容后台、累计资金闭环、商家链接与直播导流、基础数据统计。
P1：真实用户口碑分布、品牌关注更新通知、商家成员细权限、更多官方跳转 SDK、主题内容。
P2：已验证需求后的个性化推荐、用户搭配展示、更多语言与地区语境。
月榜、子品类榜不在任何计划中；只有用户后续明确改变要求才引入。

# Flutter 页面、交互与视觉规格

## 1. 全局信息架构

底部四项：发现 / 品类 / 商家榜 / 我的。品牌对比是浮动操作和独立页，不额外占底部标签。
首页内容依次为搜索框、近期选择品类、编辑推荐品牌对比、场合专题、商家入口。
品类页是大品类网格，不出现层层展开的树。

用户核心路径：
打开 → 选“电脑” → 品牌地位榜 → 品牌详情 → 加入对比 → 返回比较 → 看电脑商家累计榜 → 商家详情 → 店铺或直播。

商家路径：
某品类商家榜 → 我要打榜 → 品牌名 + Logo + 金额 → 登录/付款 → 上榜。
上榜后可进入商家中心补充介绍、店铺、直播；这些选填项不阻断核心路径。
App 中根据渠道能力显示管理能力；支付入口仅在受支持且审核允许的环境出现。

## 2. 页面与路由

| 页面 | 路由 | 主元素与关键状态 |
|---|---|---|
| 发现 | /discover | 搜索、常用品类、内容推荐；首次进入不强迫选偏好 |
| 品类 | /categories | 24 类网格、全局搜索；只显示一级 |
| 品牌榜 | /categories/:slug/brands | 当前品类、档次说明、品牌列表、筛选、榜单依据 |
| 品牌详情 | /brands/:brandId?category=:id | 首屏定位、分节内容、来源、收藏/对比 |
| 搜索 | /search?q= | 品牌/商家两个结果区，输入防抖 300ms |
| 品牌对比 | /compare?category=:id&brands=:ids | 同类最多 3 个，属性纵向对齐，关键差异摘要 |
| 商家榜 | /merchant-board?category=:id | 品类切换、累计榜、商业标记、金额说明、最近更新时间 |
| 商家详情 | /merchants/:id?category=:id | 公开档案、各品类投入、店铺/直播/视频入口 |
| 外链确认 | bottom sheet | 平台名、目标域名、离站提示、主动作、复制/取消 |
| 登录 | /login?returnTo= | 手机号、验证码、协议、错误；保留原操作 |
| 我的 | /me | 收藏、关注、设置、商家中心 |
| 商家中心 | /merchant | 我的推广品牌、所属品类、累计投入；有链接才显示导流数据 |
| 商家编辑 | /merchant/profile | 名称与Logo；选填资料在折叠区，缺失不拦截 |
| 链接管理 | /merchant/links | 类型、平台、URL、视频封面、审核和有效状态 |
| 直播管理 | /merchant/live | 直播入口、自报状态、计划时间、30 分钟有效提示 |
| 打榜页 | /merchant/contribute?category=:id | 当前累计、输入金额、预计排名、规则、支付能力 |
| 订单与结果 | /merchant/orders/:id | 待支付/确认中/成功/失败/退款状态；查后端状态 |
| 账单与数据 | /merchant/analytics | 日期范围仅筛统计，不形成另一套排名 |
| 通知与反馈 | /notifications、/feedback | 站内消息、纠错进度 |
| 设置 | /settings | 字号、主题、隐私、注销、缓存 |

手机 Web 路由可直接刷新；原生使用应用链接进入同一业务页面。登录 returnTo 只允许内部白名单路由。
未发布/已删除对象展示 404 或已下线说明；无权对象返回 403，不能凭 URL 访问他人订单。

## 3. 关键页面线框

### 品牌榜
顶部：返回 + 耳机 + 搜索
说明：看懂声音之外的品牌表达
标签：品牌地位 / 定位说明
列表：01 品牌名｜高端级｜一句话定位
      大众辨识 较高  圈层认可 中等
      加入对比
底部：榜单依据与更新时间
商业入口：查看耳机商家榜（独立模块）

### 商家榜
顶部：大品类横向选择 + 全部品类
标题：耳机商家热度榜
紧邻说明：商业推广，按累计有效打榜投入排序；不定期清零的表述禁用，统一写“累计不清零”
前三：名次 / 品牌名 / Logo / ¥28,800；仅配置链接时显示店铺或直播入口
其余：列表条目，提供同等可点击信息，避免只看前三
说明展开：累计实付、累计退款、有效打榜额与最近变更
底部：商家入驻/管理入口（平台能力允许时）

默认不显示“月度”“本周”“距离下期”等元素。
公开显示的 ¥28,800 为示意；实际必须从后端账本获得。

### 商家详情
首屏：品牌名、Logo、名次与金额。只有填了介绍或链接才呈现扩展详情。
金额区：在当前品类有效打榜 ¥X，实付 ¥Y，已退 ¥Z，名次 #N。
内容：介绍、展示图片、门店信息等全部选填，不生成空分区。
有店铺或直播链接时，才显示相应主操作；全部未填时不出现底部链接操作条。
直播按钮标注平台；自报在线用“商家标记直播中”，附最近确认时间。

### 支付页
打榜首屏只展示三个必填项：品牌名、Logo、金额；当前大品类显示为只读上下文。已有档案追加时复用名称和Logo，只输入金额。\n明确文字“购买商家展示推广服务”，展示本次所属品类。
金额预设 ¥100 / ¥500 / ¥1,000 / ¥3,000 / 自定义；这些是可配置产品默认值，不是价格研究结论。
支付前说明：当前排名、预计排名仅供参考、同类竞争可能改变名次、累计额会扣除成功退款。
提交按钮防重复点击不代替后端幂等。
回到 App 只表示用户返回；先显示“支付结果确认中”，查到服务端成功才显示成功。

## 4. 视觉方向

风格：奢侈品杂志式排版 + 清晰目录导航。大量可读留白、克制强调色、品牌名称与排名数字形成视觉重点。
不用重玻璃模糊、大面积金色渐变、赌场式撒币特效、永动跑马灯。
内容消费端有编辑感；商家金额和后台数据采用清晰工具界面。

状态必须配文字，不只靠颜色。正文和次级正文对比度至少 4.5:1，图形控件至少 3:1；交付脚本或检查报告验证实际组合。

## 5. Flutter 实施要求

- Riverpod 管理服务端状态，go_router 管理声明式路由，Dio 调用 API。
- feature-first 结构；共享 UI 与业务数据模型；支付、跳转、存储、分享、通知分平台适配。
- ThemeData + ColorScheme + ThemeExtension，禁止页面散落配色与资金算法。
- AsyncValue 明确 loading/data/empty/error；错误页有重试且保留筛选和滚动位置。
- ListView.builder/Slivers，稳定 key；不使用巨量 shrinkWrap 嵌套列表。
- 可变高度正文支持 TextScaler；禁止为了塞下金额全局关闭字号放大。
- 使用 PopScope 支持返回；从外部直播回到原列表位置；表单未保存时提示。
- dispose 控制器和订阅；异步返回后检查生命周期；Web 使用 kIsWeb/条件导入，不能全局导入 dart:io。
- 通知、相册、剪贴板等只在用户操作时请求；复制按钮不自动读取剪贴板。
- 安全存储抽象：原生凭据进系统安全存储；Web 优先 HttpOnly 会话 cookie，不能宣称 Flutter secure storage 在 Web 等价于钥匙串。

## 6. 多端适配与能力矩阵

| 环境 | 排名/内容 | 外链/直播 | 商家付款 |
|---|---|---|---|
| Android | 完整 | 系统浏览器、已验证 App Link，未安装时 HTTPS/复制 | 按发行渠道单独开通；默认走独立 Web 商家中心 |
| iOS | 完整 | Universal Links/系统浏览器，提供失败回退 | 默认关闭 App 内购买与引导；经审核的 IAP 或地区政策能力另行实现 |
| Flutter Web | 完整 | 用户点击打开 HTTPS；浏览器或宿主可能限制拉起 | 支持已开通 Web 支付；微信内浏览器和普通浏览器分别测试 |
| Windows/macOS/Linux | 自适应复用 | 默认系统浏览器和复制，不假定移动平台 SDK 可用 | 支持经过验证的 Web 收银台；不要求桌面 SDK 与手机相同 |

小于 600 逻辑像素：底部导航 + 单列；600–1023：导航栏 + 双列；1024 以上：侧导航 + 内容区最大宽度。
对比页小屏允许明确标识的横向表格滚动或逐项比较；普通页面不能整页横向溢出。
Web 分享预览与搜索抓取需要后端 HTML 元信息落地页，不能假定 Flutter Web 自动满足 SEO。

每个目标平台独立记录构建与真机测试结果。iOS/macOS 构建签名需要 macOS/Xcode；当前 Windows 设备不应被报告为已完成 iOS 打包。

# 累计打榜、资金与链接业务规则

本文件是相关业务的唯一规则源。每个大品类一个累计总榜，不清零、不按日期划分竞赛周期。

## 1. 最小打榜模型

公开条目 = 品牌名 + Logo + 当前品类有效打榜额 + 名次。
表单必填仅 displayName、logoAssetId、amountFen。categoryId 从已选品类带入；账号用于管理和付款归属，不增加经营资料字段。
店铺、直播、介绍、联系方式、地址、主体认证、品牌库关联均可缺省。
首次提交只校验名称/图片和金额；选填链接未审核或被退回，不影响无问题的基础条目。

数据术语：
- merchant：一个账号可管理的“推广品牌档案”，不是强制提供营业执照的法律主体。
- merchantCategory：推广品牌参加某个大品类的唯一累计条目。
- order：购买该条目展示推广服务的一笔订单。
- receipt：支付渠道确认的实际收款。
- rankLedger：从合格收款和成功退款派生的不可变排名流水。

## 2. 金额和排名算法

人民币 CNY；数据库 BIGINT 存分。API 为安全整数，禁止浮点元和客户端自行计算最终金额。
首版默认最低单次 ¥100（10000 分），最高 ¥100,000（10000000 分），只允许整数元；后台配置与校验响应同步。
有效打榜额的展示不扣除平台通道手续费；通道成本与平台净收入在财务侧另外核算。

对某个 merchantCategory：
grossFen = 合格成功收款所产生的 CREDIT 流水总额
refundedFen = 对这些收款的成功 REFUND 流水绝对值总额
netFen = grossFen - refundedFen
必须满足 0 <= refundedFen <= grossFen。

同一笔订单只属于一个大品类；不能同时给耳机、电脑各加全额。
同一个品牌在电脑投入 ¥500、耳机投入 ¥300，分别出现在两个榜上，不能显示为各 ¥800。
不存在将两类混排的跨品类资金总榜。财务汇总可以跨类，不能作为另一张排名。

正式排序：
1. netFen 降序；
2. attainedAt 升序；
3. merchantCategoryId 字典序升序，作为确定性兜底。

attainedAt 定义为“本条目当前净额最近一次发生变化的已提交流水时间”，由服务器生成。
退款降低净额时也更新 attainedAt，不追溯借用更早时间抢同额名次。
同一数据库时间戳可相同，最后一级 ID 让结果始终一致。
净额为零、审核隐藏、封禁条目不出现在公开付费榜，不能显示负数名次。

品牌榜与该算法没有共享评分；公开自然访问、点击也不改变资金榜排序。
金额不等于商家资产、产品质量或自然人气；首屏写明“商业推广，按累计有效打榜投入排序”。

## 3. 累计榜与退款口径

追加投入永久累积，没有到期归零或换期规则。
退款无论何时发生，都扣回原 merchantCategory，不影响其他品类；成功退款前不扣榜额。
历史快照用于审计和排查，不面向用户包装成月榜或周期榜。

公开条目可展开查看累计实付、累计已退、有效打榜额、最近变动时间。
“累计实付”仅包含获得榜额的合格订单；已扣款但待退款的异常交易在私有账单单列，不能偷偷变成排名资金。
财务所有收款都在 receipt 中记录；排名账本只接纳经过匹配的订单。两者通过异常队列对账。

条目下线：隐藏榜位并保留账本；重新审核通过后按现有有效累计重回排序。
下线不自动产生退款，也不代表拒绝应退金额；退款依据具体订单和服务协议处理。
改名/改 Logo 需版本审核，不能把无关新品牌继承为老品牌的推广荣誉；重大变更单独处理并展示变更记录。

## 4. 预计排名与订单创建

GET quote 返回：当前净额、最低/最高金额、指定追加金额、预计净额、预计名次、boardVersion、有效期 60 秒。
预计名次按请求时榜面计算，不锁定榜位。按钮写“预计升至”，不能写“购买第 1 名”。
若提供“一键超过上一名”，建议金额 = max(最低单次金额, 上一名净额 - 自身净额 + 100 分)，并按整数元约束取整。
超过单次上限时说明需要分次投入，不承诺最终位置。

创建订单：
- 要求有效登录、档案管理权限，名称/Logo 已通过基础审核，大品类启用且允许展示。
- 不检查店铺/直播/简介是否填写。
- Idempotency-Key 必填，作用域为用户 + 操作；同键同请求复用结果，同键不同请求返回 409。
- 订单固化 merchantId、categoryId、amountFen、currency、渠道、服务条款版本、15 分钟 expiresAt。
- quote 过期返回 QUOTE_EXPIRED 让用户刷新；不要提交后自动替换用户确认的金额。
- 若渠道未开通，返回 PAYMENT_CHANNEL_UNAVAILABLE，不能返回假支付成功。

## 5. 支付状态机与幂等

订单状态：CREATED → PENDING → PAID；未付款可以 CLOSED。
退款状态单独记录：NONE / PROCESSING / PARTIAL / FULL，不把 PAID 改写成“从未支付”。

渠道 success 回调处理：
1. 验签/解密，核对收款主体、渠道 App 标识、订单、CNY、金额与渠道实际成功状态。
2. provider + transactionId 唯一；一个订单只有一个 accepted receipt。
3. 获取订单与 merchantCategory 行锁；重复回调返回已处理结果。
4. 数据库事务写 receipt、PAID、CREDIT 流水、累计余额与 attainedAt、outbox。
5. 提交后再 ACK 渠道；异步失效榜单缓存，目标 5 秒内刷新。

客户端支付 SDK 返回、网页重定向、用户回到 App 都不能触发入账。
SDK 成功后先查服务端订单；用户离开收银台也不能仅凭前端取消认定未付款。
客户端自动查询最多 30 秒，之后显示“结果确认中，可稍后查看”，后台补偿查询继续运行。

迟到和异常：
- 渠道 paidAt 在订单有效时间内：即使回调晚到或本地先关单，也按真实结果入账一次。
- paidAt 超过订单有效期：记录实际收款，走异常原路退款，不增加榜额。
- 同订单不同渠道交易发生重复扣款：只有 accepted receipt 计榜，额外收款独立登记并原路退回。
- 金额/币种/身份不符：隔离收款，人工复核或退款，不能污染榜额。
- 回调乱序、重放、服务重启都靠数据库约束和事务处理，不能只靠 Redis 去重。

安全支付取值：所有金额 <= 9000000000000 分，JSON 使用整数；单次限额远低于该值。服务端累计越界则拒单。
回调原文仅保留必要审计内容；日志不记录密钥、完整支付凭证、手机号和身份证件。

## 6. 退款和对账

退款实体状态：REQUESTED → APPROVED → PROCESSING → SUCCEEDED；可 REJECTED 或 FAILED。
每笔退款必须绑定原 receipt/order，成功退款总额不得超过该收款。并发部分退款需锁定原支付行并计入已批准处理中金额做限额检查。
仅渠道确认成功后追加负流水；重复退款回调不重复扣榜。失败则不扣榜，保留原因。
关联 order 的退款影响原 category，不能用当前页面分类来选择。

政策默认：
- 重复扣款、收款与服务不匹配、技术原因未生效：全额原路处理。
- 已展示服务的退款按已告知的服务条款和实际情况审核；系统必须支持部分与全额退款，不把“绝不退款”写死。
- 管理员不能以“调整金额”修改余额；补偿更正要有独立原因、双人审批和可追溯流水。

每日对账：渠道收款/退款 ↔ receipts/refunds ↔ rankLedger ↔ materialized balance。
差异进入工单，保留责任状态。发现漏记按原交易补偿，发现重复不能删除原始流水掩盖问题。
账本、展示累计、平台收入是三种口径；跨品类汇总时只能按订单汇总一次。

## 7. 缓存和实时性

PostgreSQL 是金额真相源；Redis 仅作缓存和刷新队列。
首版数据库按复合索引排序，缓存整体榜面版本；不强依赖 ZSET 的字典序处理同额时间。
API 返回 boardVersion、updatedAt 与完整金额口径。
同一次翻页沿用 snapshotId；快照过期返回 BOARD_SNAPSHOT_EXPIRED，客户端刷新首屏，防止排序变化导致重复漏项。
有更新时显示“排名已更新，点击刷新”，不在用户手指下突然移动卡片。
支付完成页可读取强一致私有累计，并提示公开榜刷新中。

## 8. 店铺、直播和视频链接

所有链接均选填，数据存在才渲染入口。允许：
- SHOP：店铺/品牌经营页面。
- LIVE：直播间或直播主页。
- VIDEO：外部介绍视频。
- WEBSITE：介绍网站。
一个档案在每个大品类可配置多个链接；每种首版最多 3 个，指定一个主入口。

存储原始 HTTPS 地址、平台、展示标题、审核状态、可选到期时间。默认不接受用户直接提交任意自定义 scheme。
平台适配器基于已核验域名和公开官方能力生成跳转动作；未经验证的平台只做 HTTPS 和复制。
链接审核与基础条目分离：某链接不通过仅隐藏该链接。

安全边界：
- 仅 HTTPS；拒绝 javascript/data/file、用户信息 URL、内网/环回 IP、非允许域和恶意嵌套跳转。
- 服务端健康探测与预览抓取限制 DNS/重定向/出网，防 SSRF；不读取用户浏览器登录态。
- 自有出站路由只接受 linkId，不接受任意 ?url= 变成开放跳转器。
- 原生 Universal Link/App Link 白名单单独配置，失败回退 HTTPS。
- Web 在用户点击同步发起导航，避免异步 API 后打开新窗被拦截；可用预解析动作或当前页受控中转。
- 目标平台登录、App 安装情况、微信内置浏览器限制都可能影响成功；不承诺所有环境一键直达。

客户端步骤：点击 → 展示目标平台/域名 → 选择打开 → 系统处理 → 失败给 HTTPS/复制/取消。
copy-only 不弹出“跳转成功”。返回 App 保留当前页面、筛选和滚动位置。

直播状态：UNKNOWN、SCHEDULED、LIVE_CLAIMED、OFFLINE。
商家标记 LIVE_CLAIMED 最长有效 30 分钟，可续期；过期自动回 UNKNOWN。
前台写“商家标记直播中·X分钟前确认”，不能伪造第三方实时在线认证。
没有官方 API 凭证不抓取登录保护页面、不把 HTTP 200 当成正在直播。

## 9. 支付与平台能力

Apple 官方 3.1.3(g) 已核对；同一 App 广告展示的购买有 IAP 要求，例外有条件。
默认可开发闭环：独立 Flutter Web 商家中心 + 合法开通的 Web 收银台；各原生渠道显示能力由服务端 capability 决定。
iOS 首发默认只浏览与管理，不显示外部购买引导；后续可实现合规 IAP 产品与服务端交易验证。
Android 各商店/地区分别适配；不能因 Flutter 跨平台就默认同一支付插件在所有商店允许。
开发环境用独立沙箱适配器，页面明显标“演示”；生产未配置渠道时真实支付关闭。禁止通过 WebView 假装绕开商店要求。

## 10. 数据统计口径

记录 board_impression、merchant_open、shop_click、live_click、video_click、launch_attempt、launch_accepted、launch_failed、copy_link。
launch_accepted 只表示系统接受打开请求；不能解释成直播观看或订单成交。
点击有 eventId 幂等与基本去重；统计为估算有效点击，不能作为资金账本。
跨站实际观看、成交必须得到合法官方回传才另行展示。

# 技术架构与数据模型

## 1. 固定技术方案

| 部分 | 选择 | 理由 |
|---|---|---|
| 消费客户端 | Flutter stable + Dart | 用户指定跨平台，手机优先 |
| 商家中心 | 同一 Flutter 工程的独立 Web 入口/原生受控路由 | 共享模型和 UI，支付能力按环境区分 |
| 状态/导航/网络 | Riverpod、go_router、Dio | 控制业务状态、深链与类型化错误 |

### 资金数据库规则

- CREDIT：deltaFen > 0、orderId 必有、refundId 为空；每 order 只允许一条 CREDIT。
- REFUND：deltaFen < 0、refundId 必有，关联原订单；每成功 refund 只允许一条 REFUND。
- 用部分唯一索引分别约束 orderId 的 CREDIT 和 refundId 的 REFUND。
- receipts 允许记录异常重复扣款；同 order 最多一个 accepted=true 的收款。
- ledger、receipt、refund 必须归属于相同 merchantCategory；服务端事务核对关联链，不信任请求里的 ownerId。
- rank_balances 上 CHECK(grossFen>=0 AND refundedFen>=0 AND refundedFen<=grossFen AND netFen=grossFen-refundedFen)。
- 更新资金先锁同一订单/余额行，统一锁顺序避免死锁；序列化失败做有限幂等重试。
- 余额表不能接受任意外部 PATCH；后台没有“手改名次”“手改累计金额”接口。
- 应用常规数据库角色对 rank_ledger 不具备 UPDATE/DELETE；纠正追加审计流水并重新计算。
- 索引：merchant_categories(categoryId,state)、rank_balances(netFen DESC,attainedAt,merchantCategoryId)、orders(actorId,createdAt)、events(linkId,occurredAt)。

schema 与 Prisma 迁移必须实现这些约束，不能只在文字里声明。

## 4. API 约定

详细路径和必填字段以 contracts/openapi.json 为准。
base /api/v1；JSON camelCase；UTC ISO8601；ID 为 UUID；资金为整数分。
错误体：code、message、requestId、fieldErrors?、retryable。
公共读允许匿名；私有写要求认证与资源权限；后台独立 RBAC。上传和登录受限流保护。

列表返回 items、nextCursor、updatedAt；资金榜附 snapshotId、boardVersion。pageSize 默认 20、最大 50。
写接口需要 Idempotency-Key 的范围见契约。回调不使用用户 JWT，而采用渠道签名。
客户端不能提交 netFen、rank、verified、role、paymentSuccess；服务端拒绝额外敏感字段。

认证：
- 原生：短时 access token + 轮转 refresh token，刷新令牌在系统安全存储。
- Web：HttpOnly/Secure/SameSite cookie 会话，写操作 CSRF 防护；跨域白名单。
- 后台：独立会话、敏感动作二次认证；编辑/审核/财务权限拆分。
- 开发登录与假支付仅 local/test 环境；生产启动检测禁止开启。

## 5. 事件与一致性

PaymentAccepted → ledger/balance/outbox 同事务 → cache invalidation → 站内结果更新。
RefundSucceeded → 负流水/balance/outbox 同事务 → 新榜面版本。
MerchantContentApproved → 原稿替换为新 publishedVersion。
LinkRejected → 只隐藏对应链接，基础推广条目保持已通过状态。
MerchantHidden → 榜面资格隐藏；资金保留。
所有异步消费者 eventId 去重；任务失败进入重试和死信可见队列。

首版单体内事务处理资金，禁止拆成“先加钱再写账”的两个独立 HTTP 调用。
搜索使用 PostgreSQL 名称、别名、拼音和 trigram；规模需要时再接独立搜索，不先搭大搜索集群。

## 6. 配置与外部适配

必须提供接口：PaymentProvider、RefundProvider、SmsProvider、AssetStore、ExternalLinkResolver、NotificationProvider。
配置项仅写变量名与说明：DATABASE_URL、REDIS_URL、S3_ENDPOINT、S3_BUCKET、PAYMENT_PROVIDER、PAYMENT_ENABLED、APP_ENV 等。
密钥通过运行环境注入，不放移动端、不提交仓库、不输出日志、不要求用户在聊天中粘贴。

Capability API 返回环境可用功能，例如 canManageMerchant、canPurchasePromotion、paymentChannels、supportedLinkActions。

Web 商家中心使用专门会话/来源与配置；不能把 iOS 内嵌页识别为独立 Web 绕过规则。
参数只调整能力，不改变资金榜算法。

## 7. 文件、隐私与运营

Logo 上传：PNG/JPEG/WebP，<=5MB；服务端检测真实类型、去 EXIF、重编码为安全衍生图；比例 1:1；禁止用户 SVG 执行内容。
对象存储使用短时上传凭据；用户只能确认自己上传的对象。
不要求广告商提供经营资料才能上榜；平台自身收款开户和发行主体材料仍需在上线时准备。
可选联系方式默认不公开，明确用户选择后才展示；证件私有、加密、授权访问、限定保留期。
日志默认只含 requestId、内部ID和脱敏信息；用户注销不删除应依法保留的支付审计，但解除公开个人信息。
数据保留建议值是实施默认，正式发布前按主体和法域确定：业务事件明细 90 天，聚合 1 年；财务按适用要求保存。

## 8. 部署、可观测与故障恢复

开发 Compose：API、worker、PostgreSQL、Redis、MinIO；管理端与 Flutter 按启动文档运行。
生产：HTTPS、API/worker 独立进程、托管 PostgreSQL、持久 Redis、对象存储/CDN；单区域起步。
不得把此任务附带的历史服务器信息当成本次部署授权；本任务没有部署要求。

监控：错误率、P95、支付确认延迟、入账延迟、对账差异、回调验签失败、任务积压、链接失败率。
目标：内容缓存 API P95<500ms；资金服务可用性目标 99.9%；支付成功到榜面更新通常 <=5s，异常有可见状态。
每日加密备份、定期恢复演练；资金表具备时间点恢复能力。上述是验收目标，不是当前已达到的实测结果。
故障时优先停止新付款并保留阅读服务；确认渠道支付真相，修复账本后重建缓存，禁止清库解决金额异常。

## 4. 必测业务场景

### 商家最小闭环
- 仅名称、Logo、金额可完成支付与上榜；URL、电话、简介全部空仍成功。
- 当前大品类自动带入；不出现子品类必选框。
- 已有推广品牌追加，只需金额，不要求重新上传 Logo。
- 无链接时仅展示品牌资产和榜位；没有“进入空店铺”的按钮。
- 增加/删除选填链接不改变已入账金额；链接退审不隐藏无问题的基础条目。

### 资金与排行
- 一次成功收款只加一次；相同渠道交易重放 10 次仍只加一次。
- 客户端伪造成功不增加金额；验签失败和金额错误不入榜。
- 追加累积；不同品类资金隔离；累计榜跨自然月保持不清零。
- 同额先按 attainedAt 再按 ID；退款后按当前净额的新 attainedAt 排序。
- 部分退款、全额退款、重复退款回调、失败退款与并发超额退款。
- 支付与退款并发、服务重启、缓存失效、数据库事务回滚、任务重试。
- 过期前已支付但回调迟到正确入账；过期后实际扣款记录异常并原路退款。
- quote 过期、同键不同参数、同键重试、支付中断和查单补偿。
- paid order/receipt/ledger/balance/渠道对账一致；隐藏和重新上架不丢账。
- ranking-cases.json 是算法基线，不能代替真实渠道验签和数据库并发测试。

### 权限、内容和链接
- 其他商家不能改档案、看订单或申请他人退款。
- 未审核内容不作为已发布内容读取；编辑不能审批自己的发布。
- 推广展示名与品牌库名重合，不自动获得官方标志。
- 外链域名、重定向、scheme、内网地址和失效链接处理正确。
- 直播状态过期；未安装目标 App；iOS/Android/普通浏览器/微信内置浏览器/桌面回退。
- 外部返回不丢滚动位置；系统接受拉起不被统计成观看或成交。
- 退出登录清除私有缓存，公开内容可继续读。
- 账号注销、数据导出/更正、可选隐私字段处理有完整路径。

## 8. 商业验证和运营数据

北极星建议：每周完成品牌阅读并发生对比/收藏/有效外跳的用户数。
消费者漏斗：访问 → 品类 → 品牌详情 → 对比/收藏 → 商家榜 → 可选外链。
广告商漏斗：我要打榜 → 填完三项 → 创建订单 → 成功入账 → 曝光 → 追加。
主要指标：首次打榜完成率、支付确认耗时、追加率、每品类付费品牌数、商家有效外链点击率、退款率、内容纠错率。
无链接广告商主要看曝光与详情互动，不强迫其补链接，不将点击为零视为失效服务。

累计榜的商业局限：老榜头部积累后，新商家可能觉得追不上；按用户要求不借月榜解决。
可用入口：清晰的“超过上一位还差多少”、完整列表、新品类引导、商家资料分享与对比；这些不改变金额排名。
不能靠运营插队、虚假金额或暗中折算破坏公开规则。价格和转化率没有实测前不写保证收益。
