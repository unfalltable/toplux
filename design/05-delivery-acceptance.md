# 开发交付、测试与运营验收

## 1. 执行原则

交付可运行的 Flutter 客户端、真实数据库后端、运营后台和测试，而不是只有静态页面。
不因缺少支付密钥而停止开发基础闭环：先做独立、标记清楚的沙箱适配器，再完成真实适配器的接线和未开通状态。
真实收款、短信、签名、渠道审核是上线依赖，不伪装成已验证。

三条产品约束贯穿数据库、API、表单与测试：
- 品类只有“电脑、耳机”等一层大品类。
- 每个大品类仅一个不清零的商家累计榜。
- 商家打榜只需品牌名、Logo、金额；店铺、直播、介绍等选填。

## 2. 任务分解与完成条件

| 阶段 | 实施任务 | 阶段验收 |
|---|---|---|
| M0 工程与契约 | 固定依赖版本、Flutter/API/admin 工程、Compose、迁移、种子、CI、环境示例 | 一条文档化流程启动；健康检查、测试数据库和演示登录可用 |
| M1 内容浏览 | 大品类、搜索、品牌榜、详情、来源、对比、收藏；后台编辑与发布 | 24 类均可进入；匿名用户完成搜索—对比；内容草稿不泄漏 |
| M2 最小商家打榜 | 名称/Logo、上传审核、所属品类、累计榜、追加金额、幂等账本 | 三项表单即可沙箱上榜；没有任何链接仍完整工作 |
| M3 真实资金与异常 | 支付适配、验签、查询补偿、退款、对账、缓存一致性 | 沙箱端到端含重复回调、退款、断网；真实渠道需单独出具证据 |
| M4 选填扩展 | 介绍、店铺/直播/视频链接、链接审核、直播有效期、外链统计 | 可选功能失败不破坏基础榜；无死按钮；各系统正确回退 |
| M5 加固与发行 | 角色权限、审计、可访问性、性能、备份恢复、打包和渠道能力 | 验收矩阵通过；列明每个平台实际测试结果及未开通项 |

开发顺序是依赖顺序，不把 M2 以后偷换成“以后再说”的承诺。
商家榜先完成三项必填闭环，再加选填扩展，不用复杂入驻表单拖住核心功能。
不凭 AI 编码速度给出保证工期；先根据 M0/M1 实测工作量估算后续，并注明外部开通等待。

## 3. 数据准备与演示

开发 demo 环境：
- 使用 categories.json 的 24 个一层大品类。
- 每类至少 3 个带“演示”标记的品牌品类档案，不能编造真实口碑或来源。
- 商家榜各类准备无链接、仅店铺、仅直播、全部可选等样本；模拟付款明确使用沙箱标记。
- 同名品牌跨品类定位不同的样本，用于验证不串资料。
- 金额为零、全部退款、隐藏条目、名称长、Logo失败、直播过期等状态。
- 生产种子不包含演示商家、虚假支付和演示访客统计。

正式内容发布门槛：每个计划正式开放品牌榜的大品类至少 5 份已审核档案，榜单依据和版本完整。
资料不够的品类仍可用，但明确“资料补充中”；不得把尚未完成的内容说成完整权威排名。

## 4. 必测业务场景

### 商家最小闭环
- 仅名称、Logo、金额可完成支付与上榜；URL、电话、简介全部空仍成功。
- 当前大品类自动带入；不出现子品类必选框。
- 已有推广品牌追加，只需金额，不要求重新上传 Logo。
- 无链接时仅展示品牌资产和榜位；没有“进入空店铺”的按钮。
- 增加/删除选填链接不改变已入账金额；链接退审不隐藏无问题的基础条目。

### 资金与排行
- 一次成功收款只加一次；相同渠道交易重放 10 次仍只加一次。
- 客户端伪造成功不增加金额；验签失败和金额错误不入榜。
- 追加累积；不同品类资金隔离；累计榜跨自然月保持不清零。
- 同额先按 attainedAt 再按 ID；退款后按当前净额的新 attainedAt 排序。
- 部分退款、全额退款、重复退款回调、失败退款与并发超额退款。
- 支付与退款并发、服务重启、缓存失效、数据库事务回滚、任务重试。
- 过期前已支付但回调迟到正确入账；过期后实际扣款记录异常并原路退款。
- quote 过期、同键不同参数、同键重试、支付中断和查单补偿。
- paid order/receipt/ledger/balance/渠道对账一致；隐藏和重新上架不丢账。
- ranking-cases.json 是算法基线，不能代替真实渠道验签和数据库并发测试。

### 权限、内容和链接
- 其他商家不能改档案、看订单或申请他人退款。
- 未审核内容不作为已发布内容读取；编辑不能审批自己的发布。
- 推广展示名与品牌库名重合，不自动获得官方标志。
- 外链域名、重定向、scheme、内网地址和失效链接处理正确。
- 直播状态过期；未安装目标 App；iOS/Android/普通浏览器/微信内置浏览器/桌面回退。
- 外部返回不丢滚动位置；系统接受拉起不被统计成观看或成交。
- 退出登录清除私有缓存，公开内容可继续读。
- 账号注销、数据导出/更正、可选隐私字段处理有完整路径。

## 5. UI 和性能验收

- 375、390、430 逻辑像素手机，768 平板，1280 桌面；包含横屏。
- iOS 44pt/Android 48dp 最小点击区域；系统字号 200% 不遮挡关键金额/按钮。
- 浅深两套主题正文对比 4.5:1；错误、直播和付款状态不能只用颜色。
- 每个列表和详情都有加载、空、错误、重试、过期或下线状态。
- 榜单滚动更新不跳动；内容/图片预留空间，图片按显示尺寸压缩和懒加载。
- 降低动效设置生效；动画只用于反馈，不用持续闪烁与重模糊。
- 首屏可交互目标：指定中端 Android、稳定普通移动网络冷启动 <3 秒；需记录机型、网络、构建模式和数据量。
- 列表滚动目标 60fps，使用 profile/release 测量；不能用 debug 卡顿或模拟器结果代替真机结论。

## 6. 自动化与交付物

后端：单元 + Postgres 集成 + 契约 + 并发资金测试。
Flutter：金额展示与表单 widget 测试、导航/状态测试、核心路径 integration_test。
后台：发布权限与退款操作关键 E2E；不为每段静态文案写脆弱快照测试。
CI：格式化、静态检查、迁移检查、单测、可构建平台 smoke build。
将执行命令、真实输出摘要和失败项记录到 TEST_REPORT.md；未运行写未运行。

必须交付：
- 源代码、依赖锁定、数据库迁移、种子、API 文档。
- README 启动/演示步骤与环境变量模板，模板不含真实密钥。
- DEMO/PROD 清晰隔离；生产缺配置不提供假的成功按钮。
- 测试报告、实际构建产物或构建说明、第三方能力未接通清单。
- 运营后台可编辑内容与审核链接；不能要求改源代码维护全部数据。
- 不自动初始化、提交或推送用户未提供的 Git 仓库。

## 7. 发行与外部依赖清单

| 依赖 | 本地开发可先完成 | 正式上线必须具备 |
|---|---|---|
| 平台收款 | 沙箱账本与适配器 | 平台收款主体、商户号、回调 HTTPS、对账能力 |
| iOS | Flutter 共享代码与能力禁用 | macOS/Xcode、签名、商店支付路线、审核 |
| Android | 构建与外链回退 | 目标渠道资质、隐私说明、支付政策确认 |
| Web | 本地功能 | 域名/HTTPS、部署、按业务主体适用的备案与材料 |
| 店铺/直播 | 通用 HTTPS+复制 | 特定平台深链或 SDK 真机验证、必要官方授权 |
| 短信/通知 | 开发 mock | 真实服务开通；不把短信 mock 发到生产 |
| 品牌内容 | 结构和演示 | 真实来源、图像权利、编辑复核与投诉处理 |

核心商家三项输入不变。表中的“平台收款主体材料”是平台运营方的上线责任，不是给每个打榜商家增加必填资料。

## 8. 商业验证和运营数据

北极星建议：每周完成品牌阅读并发生对比/收藏/有效外跳的用户数。
消费者漏斗：访问 → 品类 → 品牌详情 → 对比/收藏 → 商家榜 → 可选外链。
广告商漏斗：我要打榜 → 填完三项 → 创建订单 → 成功入账 → 曝光 → 追加。
主要指标：首次打榜完成率、支付确认耗时、追加率、每品类付费品牌数、商家有效外链点击率、退款率、内容纠错率。
无链接广告商主要看曝光与详情互动，不强迫其补链接，不将点击为零视为失效服务。

累计榜的商业局限：老榜头部积累后，新商家可能觉得追不上；按用户要求不借月榜解决。
可用入口：清晰的“超过上一位还差多少”、完整列表、新品类引导、商家资料分享与对比；这些不改变金额排名。
不能靠运营插队、虚假金额或暗中折算破坏公开规则。价格和转化率没有实测前不写保证收益。
